**이 세션에서 할 일은 세 가지입니다.**

1. **원본 추출과 대조.** `source.mjs`의 `section()`으로 `QUIZ`·`shuffleQ`·`drawQuiz`·`quizReady`·보상 처리 문장·`quizRelated`를 그대로 추출합니다. 규칙을 새로 쓰지 않습니다.
   - 화면 일(DOM 조작)이 섞인 `renderQ`의 보상 처리는 3단계의 `judge`·`equip`처럼 원본 문장을 그대로 담는 최소 함수로 감싸고, 감싼 방법을 `source.mjs`에 남깁니다.
   - `Math.random`은 `createLegacy({random})`의 주입 난수를 쓰게 합니다. 같은 난수 열에서 원본 소스를 직접 실행한 결과와 대조하는 테스트를 넣습니다: 뽑힌 5문항, 섞인 보기 순서와 정답 번호, 보상 전후의 `extra`·`quizAt`·`quizUsed`.
   - 413문항을 어디에 둘지 정해 주세요(`legacy.mjs` 안에 그대로 둘지, `prepare.mjs`로 `data.json`에 내보낼지, 따로 불러올지). 첫 화면 불러오기 크기에 미치는 영향을 재서 근거로 삼습니다.
   - `node prepare.mjs`로 다시 만들고, 생성 결과의 차이가 추가한 구간뿐인지 확인합니다.

2. **시간 경계 판정 (Opus 5.5 high).** 이 단계에서 올려서 할 부분입니다.
   - 24시간 창: 창이 열리기 전, 창 안에서 한도 남음, 한도 소진, 만료 직전·직후(1ms 단위), 만료 뒤 첫 보상이 새 창을 여는 것.
   - 추가 출하 상한(`extra`가 이미 `quizMax()`인 상태)에서 `quizUsed`만 오르는 것.
   - 행사 한도(`PROMO.quizMax`). 원본의 행사는 모두 끝났지만 함수는 들어 있습니다. 3단계 통합 검토가 "한도가 1보다 큰 행사 기간"을 확인하지 못한 채 남겼으니, 이번에 퀴즈 쪽은 `now`를 행사 기간 안으로 넣어 대조해 주세요.
   - 기기 시계가 뒤로 간 경우(`quizAt`이 미래)와 불러온 저장의 `quizAt`·`quizUsed`가 이상한 값일 때 원본이 어떻게 동작하는지 확인하고, 불러오기 검사(`engine.mjs`)에 넣을 항목을 정해 주세요. 출하 주기(`pullAt`)의 0b단계 처리와 같은 방식이어야 합니다.

3. **엔진 명령과 화면.**
   - `engine.mjs`에 조회(남은 보상 횟수, 한도, 갱신 시각, 보유 추가 출하)와 명령을 추가합니다. 명령은 다른 명령과 같은 보호(다중 탭 검사, 손상 저장 보류, `commandBusy`, 저장 먼저 시도 후 결과 반환)와 `commandSafely`의 저장 잠금을 거칩니다.
   - 진행 중인 퀴즈(뽑힌 문항, 현재 번호, 맞힌 수)는 원본처럼 저장하지 않습니다. 저장은 결과에서 보상이 처리될 때 한 번입니다. 원본은 보상이 없을 때도 결과에서 `save()`를 부릅니다. 이것을 그대로 둘지(쓰기 한 번) 정해 주세요.
   - 채점을 어디에서 할지 정해 주세요. 정답 번호와 맞힌 수를 화면 쪽이 들고 있으면 "다섯 문제 정답"을 화면이 주장하게 됩니다. 엔진이 세션을 들고 답을 받아 채점하는 구조를 권합니다.
   - 화면: 연구 탭의 퀴즈 요약(보상 잔여 n / 한도, 보유 추가 출하, 갱신 시각 또는 "첫 보상부터 24시간 기준"), 문제(진행 n / 5, 맞힌 수, 보기 4개), 해설(정답·오답, 정답 보기, 해설, 관련 보유 소재 또는 도감 링크, 다음 문제/결과 보기), 결과(n / 5 정답, 보상 문구 네 가지, 남은 횟수가 있으면 "한 판 더"/"다시 도전", "확인").
   - 보상 직후 상단 칩(남은 출하)과 공방의 출하 버튼이 바로 바뀌어야 합니다.
   - 문항의 `<b>`를 어떻게 그릴지 정해 주세요. 체험판 화면은 `el()`로 글자만 넣습니다. 문항 HTML을 그대로 넣는다면 허용 태그를 확인하는 검사를 `prepare.mjs`나 테스트에 둡니다.
