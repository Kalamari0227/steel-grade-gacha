**배경.** 이 프로젝트는 철강 강종 캐릭터 수집 게임입니다. 승인된 원화로 만든 체험판 코드 위에 이전 게임의 기능을 단계별로 옮기는 본 개발 중입니다. 0a단계(기반 정리)와 화면 개편(게임풍 껍데기, 로비·출하소, 도감 격자·전체 화면 상세, 제목 글꼴)은 끝났고 `게임용` 브랜치의 `8eeea0e`에 커밋·푸시·배포돼 있습니다. 지금 체험판은 아직 "체험용"입니다. 새 프로필에 추가 출하 12회와 스크랩 60을 지급하고, `체험용 자원 채우기` 버튼이 있고, 체험 전용 저장 키를 씁니다. 0b단계는 이것을 원본과 같은 제품 규칙으로 바꾸는 단계입니다.

**작업 위치.** 코드는 `game-edition/.omo/prototypes/steel-companion-full-art-remake/`에 있습니다. 숨김 폴더지만 Git에 추적되는 실제 제품 소스입니다. Git 저장소는 `game-edition/`이고 브랜치는 `게임용`입니다. 프로젝트 루트는 Git 저장소가 아닙니다.

**이 세션에서 할 일은 세 가지입니다.**

1. **체험용 지급과 자원 채우기 제거.** `src/engine.mjs`가 시작할 때 `extra:12, scrap:60`을 덮어쓰는 부분과 `refill()`, 출하소 화면(`views.mjs`의 `shipyard`)의 체험 안내 문장·`체험용 자원 채우기` 버튼, `app.mjs`의 `refill` 연결을 없앱니다. 새 프로필은 원본 `S`의 기본값(추가 출하 0, 스크랩 0)으로 시작해야 합니다.

2. **정식 저장 키와 정규화.** 저장 키를 체험 전용 `steel_companion_prototype_20261109_v1`에서 기존 계약의 `sgg_game_save_v1`로 바꿉니다. 확정된 결정은 "체험 세이브는 체험용 지급이 섞여 있어 자동 이전하지 않는다"입니다. 이번 단계의 범위는 localStorage 진행 저장과 불러올 때의 정규화까지입니다. IndexedDB 사본, SGG1 백업·복원, 저장 진단, 초기화는 7단계이므로 만들지 않습니다.

3. **출하 주기.** 기본 출하는 24시간에 1회이고 그 뒤로는 추가 출하를 씁니다. 원본 규칙은 이미 `legacy.mjs`에 추출돼 있습니다(`DAY`, `readyIn`, `pullWindowOpen`, `pullRenewed`, `pullBaseLeft`, `pullsLeft`, 출하 시 `pullAt`·`pullUsed` 갱신). 규칙을 새로 쓰지 말고 이 함수들을 엔진에서 그대로 쓰게 하고, 원본과 결과가 일치하는지 대조해 주세요. 화면에서는 남은 출하가 0일 때 다음 기본 출하까지 남은 시간을 출하소와 로비의 출하 버튼, 상단 재화 칩에서 알 수 있어야 합니다. 알림·공지·기간 행사·요일별 증산은 5단계이므로 넣지 않습니다.

**구현 전에 사용자에게 확인받을 것.** 아래 넷은 저장 계약이나 제품 판단이라 근거를 조사한 뒤 제안과 함께 물어 주세요. 답을 받기 전에 그 부분을 구현하지 않습니다.

- **같은 키에 이미 있는 이전 게임 세이브.** 지금 체험판은 `sgg_game_save_v1`에 있는 값을 "다른 제품의 세이브"로 보고 건드리지 않으며, 테스트 세 곳(`qa/engine.test.mjs`의 `preserve`, `qa/prototype.spec.mjs`의 `original-progress-preserved`)이 그것을 검사합니다. 정식 키로 바꾸면 이 값이 곧 이 게임의 진행이 됩니다. 이전 게임으로 쌓은 세이브를 원본 `applySaved()` 정규화로 이어받을지, 형식이 다르면 어떻게 할지를 `docs/game-persistence.md`와 원본 소스로 확인해 제안해 주세요. 공개 주소(`kalamari0227.github.io`)에서 이전 게임을 했던 브라우저에는 실제로 이 값이 있을 수 있습니다.
- **체험판이 덧붙인 저장 항목.** 지금 저장에는 원본에 없는 `prototypeVersion`, `results`(마지막 출하 결과), `featured`(로비 대표 동료, 지정했을 때만 생김)가 있습니다. 정식 저장에서 각각을 어떻게 둘지, 이전 게임 세이브에는 이 항목이 없다는 점을 정규화가 어떻게 다룰지 정해야 합니다. `featured`의 현재 계약은 DESIGN.md의 "U2 로비와 출하소" 절에 있습니다.
- **이전 게임의 IndexedDB 사본.** 계약상 원본은 진행이 비어 있을 때 IndexedDB 사본을 확인합니다. 이번 단계에서 IndexedDB를 읽지 않으면 생기는 차이(예: localStorage만 지워진 사용자의 복구)를 설명하고, 7단계로 미뤄도 되는지 확인해 주세요.
- **검토 수단.** 제품 규칙이 되면 새 프로필은 하루에 한 번만 출하할 수 있어서 화면과 연출을 검토하기 어렵습니다. 제품에 숨은 지급 기능을 넣지 않는 것이 기본입니다. 테스트는 저장을 미리 심는 방식으로 하되, 사용자가 직접 화면을 확인할 방법(예: 로컬 전용 시드 스크립트)을 제안해 주세요. 공개 체험판을 0b 결과로 갱신할지도 이때 함께 정합니다.

**출발 기준선.** 2026-11-15 기준 `8eeea0e`에서 단위 테스트 18/18, Playwright Chromium 22/22, WebKit 22/22가 통과하고 `python3 tools/verify-current-art.py`(game-edition 루트에서 실행)가 PASS입니다. 작업 전에 이 기준선을 직접 확인하고 시작해 주세요. Playwright 설정에는 서버 자동 실행이 없어서, 테스트 전에 체험판 폴더에서 `node server.mjs`(포트 8779)를 띄워야 합니다. 서버 없이 돌리면 전부 실패로 나옵니다. 끝나면 서버를 내려 주세요.

**기존 테스트에 미치는 영향.** 지금 테스트 대부분이 체험용 지급에 기대고 있습니다. 새 프로필에서 바로 10연 출하를 하거나 1회 출하를 여러 번 하는 테스트는 그대로는 실패합니다. 테스트가 검사하는 내용(한 번만 차감, 다중 탭 거부, 손상 저장 보류, 결과 보존 등)은 유지하고, 시작 자원을 저장에 미리 심는 도우미로 바꿔 주세요. 검사 자체를 약하게 만들거나 지우지 않습니다. `refill` 단위 테스트는 기능과 함께 없앱니다. 고친 테스트는 무엇을 왜 바꿨는지 목록으로 남겨 주세요.

**추가할 검증.**

- 엔진 단위: 새 프로필의 시작 자원이 원본과 같음, 기본 출하 1회 뒤 남은 출하 0, 24시간 경계 직전·정확히·직후(엔진의 `now` 주입 사용), 기본 출하를 먼저 쓰고 그다음 추가 출하를 쓰는 순서, 원본 함수와 같은 난수에서 같은 결과.
- 저장: 정식 키로 쓰고 다시 읽음, 체험 키의 값은 읽지도 지우지도 않음, 손상 저장·다른 탭 변경·쓰기 실패에서 기존 보호가 그대로 동작함, 위에서 확정한 방식대로 이전 게임 세이브를 처리함.
- 브라우저(Chromium·WebKit): 새 프로필이 1회 출하 뒤 출하 버튼이 비활성이 되고 남은 시간이 보임, 시간이 지나면 다시 가능함(Playwright의 시계 제어 사용), 390px·1280px에서 가로 넘침 없음과 44px 조작 영역.
- 저장을 건드리는 단계이므로 개발 계획의 원칙 5(다중 탭·손상 저장·저장 실패)를 반드시 포함합니다. 저장·정규화의 최종 검토는 프로젝트 지침(`AGENTS.md`)의 상위 검토 대상입니다.

**끝난 상태.** 새 프로필이 원본과 같은 자원으로 시작하고 하루 한 번 출하하며, 체험용 지급과 자원 채우기가 코드·화면·테스트에서 사라지고, 정식 키로 저장·복원되며, 위 검증이 Chromium과 WebKit에서 통과하고, `verify-current-art.py`가 PASS입니다.
